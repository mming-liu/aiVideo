# U6 R6：冻结身份可复现化 + 矛盾自检词表外置（2026-11-14）

> 本文替换 R5 作为**待送审对象**。R5 的内容修订一条没退，R6 只改两处**判据层**：
> ①质量报告的字节级不确定性；②prompt 矛盾自检里写死的作品措辞。
> 全程零模型调用：没有发出任何请求，`output/` 下正式产物一个字节未动。

## 1. 一句话结论

R5 的 `quality_sha256` **不可复现**——同一份分镜、同一套规则，连续重建两次得到两个
不同摘要（`cb08db51…` / `7fbc5863…`）。冻结候选的核心承诺是"别人能重算出同一个
身份"，这条不成立，后面所有审计都建在沙上。修掉它，顺带把最后一处绑作品的词表
外置，因此有 R6。

## 2. 两处改动

### 2.1 质量报告的字节级不确定性（**缺陷，必须修**）

- 现象：`r6_build.py` 连跑两次，`candidate_sha256` 完全一致（分镜字节没变），
  但 `quality_sha256` 每次不同。
- 根因：`step01_script_gen/validation.py` 规则 13.7（出镜角色服装色重述）把
  `known_chars` 这个**集合**直接拼进 advisory 文案：
  `f"{label}: 未重述出镜角色关键服装色 {missing_dress}"`。
  集合迭代顺序随 `PYTHONHASHSEED` 变化 → 文案里两个名字的先后变化 → 报告字节变化。
- 修法：拼接前 `sorted(known_chars)`。排序键是角色标识符，与内容无关。
- 证据：`PYTHONHASHSEED=0/12345/999` 三次重建 → **同一摘要 `9843de08eba47e0d…`**。
- 回归：`tests/step01_script_gen/test_quality_report_determinism.py`（3 条）钉住
  "集合插入顺序不影响文案"与"文案内名字按码位有序"。
- 影响：`validation.py` 在 `RULE_SOURCE_FINGERPRINT` 清单内，所以指纹必变；
  `RULE_VERSION` / `QUALITY_RULE_VERSION` 一并升到 `2026-11-14.1`。

### 2.2 矛盾自检词表外置（**通用性**）

`shared/prompt_contradiction.py` 原先在函数体里写死四组词，其中两组是从 2026-08
某一本书的真实 prompt 提炼的**本作措辞**（`「伤处白袍」「一片暗红血迹洇开」`、
`黑影/人影`）。换一本没有"白袍伤描写"也没有"水下黑影伏笔"的书，判据永远不触发——
代码看起来在跑，实际只对一本书生效。

现在拆成两层：

| 层 | 文件 | 内容 |
|---|---|---|
| 数据 | `shared/prompt_contradiction_lexicon.py` | 默认词表（通用中文视觉词汇）+ 覆盖加载 + 校验 + 缓存 |
| 判据 | `shared/prompt_contradiction.py` | 只保留**结构**：同 holder 的持有/否认、禁令禁掉前文需要的东西、前态与伤情结束态同现 |

判据结构（与题材无关）：

- **C1 持有/否认对称矛盾**：同一 holder 既"持有 X"又"手里没有 Y"，且 X/Y 同类（`blade_terms`）。
- **C2 禁令 vs 需要**：`禁止…` 子句里出现的实体，是否在前文被需要。`真人影视剧`
  这类风格前缀造成的跨词命中按 `prohibition_ignore_substrings` 排除。
- **C3 前态 vs 伤情**：前态词 + 伤情词，且伤情**落在身体/衣物上**（`body_or_garment_terms`
  窗口），且两者净间距 ≤ `pre_state_max_distance`。
- C4 描述块重复注入（24 字滑窗）、C5 双标点：本来就与内容无关，未动。

覆盖方式（项目级增量，不复制默认值）：

```
PROMPT_CONTRA_LEXICON=config/prompt_contradiction_lexicon.json
{"schema":"prompt_contradiction_lexicon.overlay.v1",
 "add":{"injury_terms":["吐血"]},"set":{"prohibition_mode":"enumerate"}}
```

未知键 / 非法 mode / 坏 JSON / 覆盖文件缺失 → `LexiconError`（配置写错字不许静默失效）。
`prohibition_mode="enumerate"` 可从「禁止…」子句机械切词，但切词有噪声，**默认关闭**。

#### 精度取舍（有实测依据，不是猜的）

第一版把静态血迹词（`暗红`/`血迹`/`血痕`/`伤处`）也算"伤情结束态"，在真实候选上
**立刻误报 6 段**：

```
杨旭仰倒画左船头，心口暗红；张十三右手尚未扬起     ← 前者旧伤、后者动作未起，并不矛盾
杨旭…心口衣料暗红洇痕，…双脚尚在地面、尚未进入车厢  ← 同一人不同方面
```

结论：静态血迹词表示"伤一直在"，与"尚未发生"不冲突；只有"刺入/洇开/渗血/中刀"
这种**此刻正在发生**的词才构成矛盾。默认表据此收窄，并把这段原因写进代码注释与
`tests/shared/test_prompt_contradiction_lexicon.py::test_defaults_do_not_include_static_blood_words`。

#### 行为等价证据

同一批语料（R4/R5 候选 13 镜 × prompt/ff_desc/lf_desc/motion_desc/keyframes/
layout desc + R5 Step02a `--plan-only` 的真实组装 prompt + 历史快照）共 **342 段**：

| | 旧版（git HEAD） | 新版 |
|---|---|---|
| 命中段数 | 0 | 0 |
| 裁决不一致 | — | **0** |

即：换词表重构后，本作语料上的裁决**逐段不变**；泛化能力由新增夹具包证明（见 §4）。

## 8. 未做 / 风险

1. **`tests/step01_script_gen` 全量一次跑 47 条红——根因已更正为本机删除审计门，
   不是用例失败**（本节前一版把根因写成"凭据路径自相矛盾"，是错的，据此更正）：

   - 现象：整个目录一次跑完 → 47 failed / 4279 passed；同一批文件分成 12 组
     分别跑 → **4328 passed / 0 failed**（见第 9 节）。
   - 唯一失败形态：`[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]
     {"count":50,"threshold":50,"scope":"turn",...}` → 进程被 `SystemExit(1)` 打断。
     47 条失败与 47 条该标记**一一对应**（`grep -c` 实测），无一例外。
   - 机制：本机 Python 启动钩子（`sitecustomize.py` 的 `_check_bulk_delete_guard`）
     对**删除**做累计审计，一个进程内累计超过阈值（本机 50）就拒绝执行，
     并以 `SystemExit(1)` 结束进程。测试套件本身要删几百个临时文件，必然越线。
   - 为什么"分组跑就绿"：预算按**单个进程**算，一个 pytest 进程就是一份 50 的额度；
     换一个进程（换组）重新从 0 开始。所以这不是偶发，也不是用例之间的状态污染
     ——分开跑能稳定复现绿，合起来跑能稳定复现红。注意它**不跨工具调用累计**：
     本轮同一回合内前一次调用已越线，下一次仍从 0 开始（实测，见第 8 节第 4 条）。
   - 顺带修掉一个**真缺陷**（本轮改）：`_create_adoption_receipt` 原先
     "先写 `step01_adoption.json.tmp` → `verify` → 失败就 `unlink`"。
     那次 `unlink` 正好落在删除审计上，于是真正的失败原因（`chapter_dir_mismatch`）
     被"进程被审计打断"顶掉——日志里只剩退出码 1。现在改为**先验后写**：
     `validate_receipt()`（新拆出的纯字典校验）+ `verify()` 全在内存里跑完，
     通过才落盘；失败路径**一个文件都不写也不删**，返回
     `create_failed:<稳定 code>: <消息>`。用例见
     `tests/step01_script_gen/test_step01_commit.py::test_adoption_receipt_failure_leaves_no_file_behind`
     与 `::test_adoption_receipt_writes_once_after_verification_passes`。
   - 仍然存在的**测试侧**事实：47 条里 27 条确实走到了 `chapter_dir_mismatch`
     （夹具 patch 了 `m.CHAPTER_DIR` 却没 patch `OUTPUT_BASE`/scope，凭据自相矛盾，
     `verify` fail-closed 是对的）。这条分支现在只是**干净地返回 create_failed**，
     不再顺手删文件，于是不再放大成进程退出。
2. **`prompt_contradiction` 不在 `RULE_SOURCE_FINGERPRINT` 清单里**。它决定 step02a
   的 `visual_plan_blocked`（真实生成入口 `SystemExit(2)`），但 step01 的质量报告
   身份不含它——也就是说"改了矛盾判据"不会让旧质量报告失效。本轮**没有**把它加进
   指纹：加了会再次改写所有已采纳报告的身份，属于另一个决策（是否要给 step02a 判据
   单独建一套身份），建议单独立项。
3. `prohibition_mode="enumerate"` 的切词精度只在本轮夹具上验证过，**没有**在真实
   长 prompt 语料上做误报普查；默认关闭就是为此。
4. **删除审计门的预算是"每进程 50 次"，不是"每回合"**（本轮补测更正）。同一回合内
   先后 5 次调用，前一次已经把计数顶到 50，后一次仍从 0 开始——所以按文件分组跑能
   稳定复现绿。据此把两个套件重跑到底，读数见第 9 节：`tests/shared` 与
   `tests/integration` **均无真实失败**，只剩 1 条用例受环境硬限制：
   `test_chain5_artifact_protection.py::test_transaction_tool_reports_production_unchanged[merge]`
   自己的子进程单次要删 64 个文件（`count:64`），必然越线。同一条用例的 `[tts]`
   参数在其后单独跑是通过的，证明失败点在删除配额而非被测逻辑。
   另有一类**级联**现象值得记：被门打断的工具会把 `.lock` 留在原地，同一进程里的
   下一步再拿锁就报 `lock_busy（alive）`——那个"存活"判定当时是**正确的**（持有者就是
   正在跑的自己），进程退出后 `owner_status()` 立刻返回 `pid_dead`。
   `tests/integration` 首轮 20 红里有 6 条属于这种级联，文件单独跑即绿。
5. 仍剩 213 个测试文件把作品词内联在代码里（棘轮已钉住只降不升），其中 23 个是申报过
   的历史抓取件。
