## 一、WP1a：图片预算账本自动发现（根治 §6.2）

### 1.1 事故形态

R6 S07 实跑前我漏传了 `STEP02A_IMAGE_BUDGET_TOTAL`。后果不是"报错"，是**静默失效**：
章目录里躺着 `step02a_image_budget.json`（`used=31 / limit=172`），而 `post_budget`
的启用判据是 `TOTAL > 0`，环境变量没给就直接 `return None, 0`——门禁整条旁路，
2 次 POST 照发，账本一动不动。事后只能靠 `step02_events.jsonl` 里的 `200` 反推补记。

**危险点在于"看不见"**：`step02a` 的预检输出里当时没有任何预算字段，护栏是否生效
只能靠翻账本才知道。

### 1.2 改法

`shared/post_budget.py`：`_config()` 拆成 `_config_detail()`，启用判据从"只看环境变量"
改成四级优先：

| 情形 | 结果 | `source` |
|---|---|---|
| `*_BUDGET_TOTAL > 0`（显式） | 按该上限启用 | `env` |
| `*_BUDGET_TOTAL` 显式 `<= 0` | **显式关闭**（唯一合法的关法） | `explicit_off` |
| 只给了 `*_BUDGET_FILE` | 从该账本读 `limit` 启用 | `ledger_env_file` |
| 环境变量全空、章目录已有账本 | **自动绑定该账本，上限取文件里的 `limit`** | `ledger_autodiscovered` |
| 都没有 | 不启用（与历史版本一致） | `disabled` |

配套三条口径：

1. **账本在 → 门禁在**。只有显式写 `TOTAL=0` 才算"我不要门禁"，避免"手滑删一行环境
   变量就裸奔"。
2. **读不懂也不放行**。自动发现到的账本即使上限读不出（损坏/字段缺失）也照样启用，
   `limit=0` 交给 `_read()` 判死，fail-closed。
3. **`reset()` 不碰自动发现的账本**。`reset(kind)` 走 `_config(discover=False)`，只删
   显式启用的账本——否则一次 `post_budget.reset()` 就能抹掉生产账本（这条单独写了用例）。

另加 `post_budget.describe(kind)`：**只读、不建锁文件**的落点窗口，供 plan-only/预检
使用（`usage()` 会开 `*.json.lock`，在"只读预检对章目录零写入"的场合是一笔多余写）。

`step02a_frame_gen` 的零调用预检输出新增 `image_budget` 字段（`enabled / source /
used / limit / remaining / path`），让"这次护栏有没有生效"直接出现在读数里。

### 1.3 实测

真实生产章、**一个 `STEP02A_IMAGE_BUDGET_*` 都不设**：

```
{"source": "ledger_autodiscovered", "limit": 172, "used": 33, "remaining": 139}
```

### 1.4 用例（`tests/shared/test_post_budget.py`，7 条新增）

自动发现即生效并扣减 / 无账本仍不启用 / `TOTAL=0` 才关闭且不改写账本 /
显式上限优先且不一致仍拒绝 / 损坏账本 fail-closed / 上限读不出不静默放行 /
`reset()` 不删自动发现账本。模块 autouse 夹具顺带把 `chapter_dir` 钉到本用例
空目录（否则会被 `.pytest_tmp` 里别的用例残留账本点亮）。

## 二、WP1b：`--plan-only` 真正的零写入（根治 §4.1 / §8.4）

### 2.1 先证伪"只有一个洞"

原判断是"`step02b --plan-only` 往章目录写 `step02.log`"。修掉 `vimax_bridge._bridge_log`
（硬编码 `chapter_dir()/step02.log`）后重跑真实命令，**仍然 exit 3**，但这次
`isolation_violation` 换成了：

```
modified: shots/2/ref_compose_ff.json, shots/2/ref_compose_lf.json
```

即 `build_plan` 阶段重写了两份参考组合清单——内容只差一个 `at` 时间戳，字节却变了。
所以"plan-only 零写入"实际有**两条**独立的写路径：

| 写路径 | 位置 | 为什么会写正式目录 |
|---|---|---|
| 桥接日志 | `_bridge_log`、`gen_shot_frames` 首/尾帧、关键帧、`submit_poll`、`continuity` | 硬编码 `chapter_dir()/step02.log`，无视日志上下文 |
| 参考组合清单 | `ref_compose.fit_refs` → `_write_compose_report` | 只认传入的 `sheet_dir`，不知道"现在是只读预检" |

### 2.2 改法

1. **日志落点统一到 `shared.log_utils.resolve_log_file`**（本来就是"唯一落点判据"）：
   `shared/vimax_bridge.py`（`_bridge_log` + 首帧/尾帧/关键帧三处）、
   `step02_video_gen/continuity.py`（2 处）、`step02_video_gen/submit_poll.py`（2 处）。
   生产上下文为空时行为与旧版完全一致；候选模式自动落实验根。
2. **参考表落点加进程级上下文**：`shared/ref_compose.py` 新增
   `set_ref_dir_context(path)` / `current_ref_dir()`，`fit_refs` / `fit_flat` 入口把
   `sheet_dir` 映射到 `<上下文>/<原目录名>`。与 `log_utils.set_log_context` 同一套思路。
   未设上下文 = 旧行为（写成用例钉住了）。
3. `_plan_only` 自兜两层：日志上下文为空就自己钉到候选实验根；`build_plan` 前后
   `set/restore` 参考表上下文（`try/finally`，异常也不漏）。
4. **`shared/style_prefix.py` 的同类改动已回退**——`sanitize_prompt` 在
   `_STEP01_STYLE_PREFIX_SYMBOLS` 里，改它会让 `RULE_SOURCE_FINGERPRINT` 从
   `d3ab095ffa4c501a` 变成 `b449ff65bd60378d`（实测）。指纹稳定性优先，这条留到 R7。

### 2.3 端到端实测（真实生产章，非测试桩）

| 阶段 | exit | `production_unchanged` | 违规明细 |
|---|---|---|---|
| 只修日志 | 3 | false | `modified: shots/2/ref_compose_ff.json, ref_compose_lf.json` |
| 日志 + 参考表都修 | **0** | **true** | — |

`step02.log` 在章目录的 mtime 仍是 20:15（S07 真实生成留下的），两次 plan-only
（20:43 / 20:47）都没有新建或追加。参考组合清单停在 20:43，第二次运行未触碰。

**如实披露**：第一次 plan-only（20:43）把两份 `ref_compose_*.json` 的 `at` 时间戳
刷新成了 20:43。两者除 `at` 外逐字段相同（同一批 inputs / outputs / regions），
未被 `step01_*` 身份清单引用，也不在 R6 采纳的四份产物里。

### 2.4 用例

## 四、WP2：`shot 2 FF` 只读 QC 补检（§6.3）

脚本 `.dsh/u6_closeout_20261110/r6_s07_shot2_qc.py` 加了三条硬约束：

1. **图片身份前置校验**：文件 `sha256 == 4089f234ff475f7a…` 且内容哈希
   `06ab04ab252884f8`，不一致直接 exit 4，拒绝在"另一张图"上补检。
2. **0 图片 POST 的证据化**：以账本 `used` 前后一致为准，不再只是口头声明。
3. **首调即停**：只有一次 `qc_image` 调用；若返回 429/rate limited，**不重试、不改写
   sidecar**，直接 exit 5 并打印 `rate_limited`（2026-11-14 连试 3 次全 429 的教训）。

### 实测结果（1 次调用，未重试）

```
图片 sha256（检前）: 4089f234ff475f7a7053975cd26e0a9e347e17eec99feb8aab153708f070389e
内容哈希: 06ab04ab252884f8 | 期望 06ab04ab252884f8 | 一致
图片账本（检前）: {"used": 33, "limit": 172, "remaining": 139, "source": "ledger_autodiscovered"}

{"rate_limited": true, "image_unchanged": true, "image_posts": 0,
 "budget_used_before": 33, "budget_used_after": 33}
exit=5
```

**结论：限流仍未解封**。sidecar 保持 `qc_call_failed`（原样，未追加失败历史），
图片字节未变、账本 33/172 未动、0 次图片 POST。本次消耗 **1 次** QC 调用。

通道恢复后重跑同一脚本即可，不需要重新生成图片，也不会动账本。
