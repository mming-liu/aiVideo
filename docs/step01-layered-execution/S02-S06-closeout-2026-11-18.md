## 1. S02-C1 缓存消费与故障分支

### 1.1 已修的两处身份不同源

1. **缓存消费者不按 prepared 组装**（原 `main.py` 只在非 auto 时组装、且不传 prepared）：
   现由 `build_prepared_facts()` 统一组装一次（`step02_video_gen/submit_poll.py`），
   `provider/model_id/capability_revision` 与提交同源；`_submit_video_candidate()`
   复用该事实，**不再二次 prepare**。
2. **plan 与提交 key 不同源**：`build_frozen_for_shot()` 现把 prepared 的
   provider/model/capability_revision 写进冻结；`build_plan()` 优先读取 Step02a
   落盘的 `visual_plan.json`（与提交同一份执行要求摘要），scope 统一为
   `scope_identity`（chapter/book_index/book_name）。

### 1.2 故障分支口径

| 事实状态 | 快照存在 | 行为 |
|---|---|---|
| `prepared` | 任意 | `cache_decision(frozen_request=...)`；auto 也核对 |
| `blocked` | 任意 | 不查缓存；交提交入口统一记录失败，**0 POST** |
| `unsupported` | 无 | 允许旧兼容：`cache_decision(frozen_request=None)` |
| `unsupported` | 有 | 禁止 legacy 命中；提交入口记 `prepared_unsupported` |

`PreparedFacts.status/code/message` 为结构化字段，不解析字符串。

### 1.3 额外修正：prompt_hash 不再随 `MERGE_AUDIO_MODE` 抖动

`_get_shot_hash()` 删除了 `merge_audio=` 分量：该配置只影响后处理/声音合同，
不改变视频模型输入。有声模型的失效由 `request_key` 的 `audio_policy` /
`effective_merge_mode` 承担；无声模型因此可精确命中。

## 3. S02-C3 有声 payload 对照

固定 shot/素材/模型，仅切 `MERGE_AUDIO_MODE`，两组都走
`_build_prompt()` → `_make_request()` → `prepare_request()`：

| 字段 | native | tts_mix |
|---|---|---|
| prepared.prompt | 相同 | 相同 |
| prepared.parameters | 相同 | 相同 |
| prepared.materials | 相同 | 相同 |
| effective_merge_mode | `native` | `tts_mix` |
| generation_requirements | `{"audio_policy":"native"}` | `{"audio_policy":"tts_mix"}` |
| request_key | 不同 | 不同 |

结论：视频 payload 未变；key 差异来自后处理声音合同。本轮保留保守行为
（收窄 key 另议，需先量成本）。无声模型对照：payload 相同、key 相同。
