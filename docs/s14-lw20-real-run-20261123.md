## 处理意见

1. **不再按现行设计追加 20 轮实跑。** 同一机制下已有 273 次 POST、0 通过，失败原因稳定可分类，
   再跑只会重复同样的读数。下一次实跑前，先用这 40 份冻结首答做离线回放验证修法。
2. **修订协议本身是计划层的主阻塞（离线可修，0 调用）：**
   - 删除提示里「不能保留主张时返回空 edits」这一出口；schema 要求对每个被点名的 id 恰好给一条修订。
     59 次空回答大多发生在合法候选存在的情况下（第 1 章 20/20 轮都有）。
   - 候选清单压缩到每句 ≤ 3 条完整句（当前一条超限句会列出几十个「不……」「就……」之类碎片），
     清单只列可改行，锁定行只给 id 和估时。
   - 允许保留合法的部分进展：通过校验的局部修订成为第 2 轮的新基线（仍单调下降、仍只开放剩余超限项），
     而不是整份丢弃再从原稿重来。
3. **第 2 章需要内容裁决（按 11-22 口径留待用户决定）：** 首答普遍把长对白整段放进声音，且 11/20 轮
   有必保留声音无合法短句。可选：次要背景事实不绑声音（改画面或省略）、拆成两集、或放开「同一引语内
   跨句截取」的逐字规则。仅靠 prompt 上限不能解决。
4. **计划过关后，分镜阶段总时长是下一个阻塞：** 5 份候选都在 95–118s，而声音只有 28–60s，超出部分来自
   分镜的镜数/画面时长分配，不是声音。建议把计划的目标时长和镜数上限显式传给分镜请求并在生成前核对；
   这属于分镜契约，不在本轮轻量修订范围内，需单独立包。
5. **预算与审计：** 首稿 ~265s 后剩余预算不够一轮修复；终审 300s 上限 20 轮中 2 次超时。是否调整
   1200s/300s 属于用户已定参数，本轮未动。
6. 基础设施失败（1 次 SSL）按调用失败处置，不计入修法评估。
