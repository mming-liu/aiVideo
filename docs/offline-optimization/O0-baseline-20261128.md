## 2. `RULE_SOURCE_FINGERPRINT`：同一提交在本机有两个值（重要）

| 口径 | 值 | 说明 |
| --- | --- | --- |
| 本机工作树（生产门禁实际比较值） | `6f612fa3d96482bb` | `python -c "from step01_script_gen.quality_issues import RULE_SOURCE_FINGERPRINT"` |
| 干净 `git archive` / LF 形态（计划预期值） | `ee3a664ccfefb5ca` | 同一命令在 `git archive HEAD` 解包目录内计算 |
| 正式章节 `step01_quality.json` 记录值 | `e5460e55f36d1d08` | 两章一致（2026-11-26 采纳时） |

根因：`_compute_rule_source_fingerprint()` 对清单内 `.py` 走**整文件字节**哈希，
而本机 `core.autocrlf=false`、`.gitattributes` 只对 `baselines/**` 与少数 docs 强制
`-text`，因此 Windows 检出把 `step01_script_gen/constraints/**`、`prompt_semantic/**`、
`shared/style_prefix.py` 等等价写成 CRLF；干净 archive 是 LF。

- 实测：`constraints/lf_desc_length.py`、`prompt_semantic/registry.py`、`shared/style_prefix.py`
  均为 100% CRLF；`timecode.py`、`quality_issues.py` 为 LF。
- 实测：逐一比对指纹输入 68 个文件与 `HEAD` blob，差异全部是「本机比 HEAD 多 N 字节」的换行差异，
  无内容改动（探针：`.tmp/o0_20261128/`，脚本见下表命令）。
- 结论：**计划里的 `ee3a664ccfefb5ca` 是 LF 形态值，本机门禁比较的是 `6f612fa3d96482bb`。**
  二者都对同一个 `6a4a3e7` 成立；差异本身就是 O2「AST 归一化去掉换行噪声」要消除的问题。
  O1 及之后各包的指纹对照以本机工作树值为准，并把两个值同时记账。

## 6. O0 附带发现（不阻塞，记入残余）

1. `--print-refresh` 在 Windows 默认代码页控制台下，chapter_001 的载荷含 `⇒` 触发
   `UnicodeEncodeError: 'gbk' codec can't encode character '\u21d2'`（`_print_json` 直接 `print`）。
   取证时以 `PYTHONIOENCODING=utf-8` 运行即可；O6 落盘前同样需要设该变量，或由调用方改用
   `--out`（`print_effective_config` 已有此参数，`production_context` 没有）。
2. 视频请求的 `size` 在 `step02_video_gen/prompt_builder.py:1725` 固定为 `"720x1280"`，
   与 `VIDEO_SIZE=1440*2560` 只是「恰好同为 9:16」。任何按 `req.size` 推导画幅的改动
   都必须知道这一点：改 `VIDEO_SIZE` 不会自动改变 `req.size`。
3. 分组测试跑在仓库根目录时会被正式 `output/` 与 `.env.content` 影响（见 5.1），
   现有 runner 未隔离 `OUTPUT_BASE`；「干净检出即可复现」尚不成立。留待后续包处理。
