### 1.1 三个数据陷阱（本批新增，必须记下）

1. **`run_id` 是「提交点进场时刻」，不是进程启动时刻。**
   生成 / 拆镜 / 结构重生成都在它之前，只按 `run_id` 过滤日志会把 P3 的结构轮与生成期证据整段漏掉（实测：`[STRUCT]` 行全部落在 `run_id` 之前）。本报告的窗口取 `step01_metrics.json` 的 `run_started`（进程启动）。
2. **崩溃的运行不写自己的 BLOCK 清单。**
   顶层 `except → [FATAL] → sys.exit(1)`，章节目录里留着的是**上一轮**的 `step01_commit.json` / `step01_metrics.json` / `step01_timing.json` 与日志切片，而驱动照常归档 → 逐次表会把上一轮的数字当成这一轮（主批 run 07 与 run 10 都踩到：读者看到的 `blocking=12` / `22` 是 run 06 / run 09 的数字）。判别方式：`rc != 0`，或同一 `run_id` 在两次运行里出现。
   `.tmp/agg_run10b.py` 已按这两条做窗口与陈旧识别，无效样本一律不进合计。
3. **`snapshots/candidate_pre_bestguard_*.json` 会滚动淘汰旧稿。**
   实测：A 批的候选稿从 17 份被后续跑挤到 11 份——**任何跨批对比都必须在两批都还在时冻结副本**，否则分母会随时间变化（本报告用的是冻结副本 `.tmp/run10b/candidates_frozen/`：A 批 10 份 143 镜、B 批 11 份 149 镜，其中 A 批 143 镜/313 帧与 A 报的读数逐字一致，可交叉核对）。

### 1.2 与 A 批的一个非代码差异：传输

本批共 **4 次**网络异常事件、涉及 **3 个运行**（01 / 03 / 08，其中 run 08 一次运行里两处）；A 批 10 次里 0 次。**事件数与运行数不是一个口径**，两个数都给，避免被读成「4 个运行」：

| 时间 | 环节 | 后果 |
|---|---|---|
| 08:03:41（run 01） | 最终语义审计 `request_failed: Connection error` | 直接 BLOCK，0 修复轮（`request_failed` 按既定策略不重试，[audit.py:501](../step01_script_gen/audit.py#L501)） |
| 08:26:06（run 03） | 提交阶段 `ConnectionResetError(10054)` | provider 自身 `2s 后重试 (1/2)` 兜住，无后果 |
| 09:39:49（run 08） | 定向修复调用 | 重试一次仍失败 → `修复调用失败/响应不完整` → BLOCK |
| 09:26:23（run 08 生成期） | 候选生成 | 重试兜住 |

所以两批的对比里含一个与代码无关的环境项；A 批的「0 次传输失败」不代表代码更稳。

### 4.1 P3 为什么是净负（11 次触发逐条）

```
run01 缺帧 2  → 重生成 → 2 → 3 个非法镜头                       → 拒
run02 缺帧 3  → 重生成 → 改善 3→1，新 blocking 身份 5 类          → 拒
run03 缺帧 14 → 重生成 → 改善 14→10，新 blocking 身份 20 类       → 拒
run04 缺帧 12 → 重生成 → 改善 13→5，新 blocking 身份 10 类        → 拒
补跑S1 缺帧 3  → 重生成 → 恶化 3 → 17 个非法镜头（缺帧 3→13）      → 拒
补跑S2/S3      → 同样触发结构轮，同样未采纳（§2 补跑表）
```

- **成本**：`regen_structural` 阶段实测 **198 / 198 / 256 / 257 / 246s**（A 批同阶段多为 20–72s），11 次合计约 **45 分钟**。
- **收益**：**0 次采纳**（`采纳新稿` 在 13 次进程的日志里出现 0 次）。
- **副作用**：run 03/04/05/06/09 的总耗时 931/941/981/912/935s 全部**越过 900s 预算**，`[COMMIT] 总预算超时，停止 final audit 修复轮` → 修复轮被截断在设计轮数之前（run 05 跑了 4 轮、run 03 三轮回落到 23 条时仍在净改善）。
- **机制**（读码）：结构轮是「重做 shot-plan」的**整篇重写**，而候选验收 `_blocking_not_degraded` 要求「**零新 blocking 身份**、既有身份次数不增」。整篇重写会改动镜头切分与内容 → 新身份经常出现。但**不能把 11 次被拒全部归因于身份变化**：日志里的拒绝理由同时含**真实台词丢失**与**完整性退化**（run 03 的 `新 blocking 身份 20 类` 里就有 `multi_person_staging`、`shot_content_over_cap` 这类真实新增问题；补跑 S1 的候选更是恶化到 17 个非法镜头）。准确表述是：**「零新 blocking 身份」这道门与「整篇重写」这种改法方向相反**，叠加 4 分钟/次与 0 采纳的实测，这条杠杆不值得保留。身份键本身已做数字归一（[main.py:499](../step01_script_gen/main.py#L499)），所以不是重编号造成的假象；但 `frame_id`（`kfN`/`segN`）**不参与归一**，KF 类问题在重写后会换身份——这条无法在本批验证（被拒候选没有落盘），列为下轮取证项。

## 5. 本批新暴露的缺陷（按影响排序）

### N1 ★ 只产出 warning 的校验器能把整次跑打死：`KeyError: '杨旭'`（P0，1/10 次）

run 10 在**候选生成阶段**（182s、仅 1 次生成调用）崩溃：

```
[FATAL] KeyError: '杨旭'
  validation.py:463   _validate_script
  validation.py:4395  _run_prompt_checklist
  validation.py:6457  _check_kf_temporal_consistency
```

根因（**既有缺陷**，`git show HEAD` 同处逐字相同）：**角色名映射与姿态类别映射混用**。

- `_extract_state_markers(text)["poses"]` 的键是**姿态类别**（`_SUBJECT_POSE_WORDS` =
  `reclining` / `sitting` / `upright`），它只能回答「这一帧有没有人躺下」，**答不出是谁**；
- `_extract_named_poses(text, shot)` 的键才是**角色名**（同子句限定，v6.62 通用化）；
- 而告警拼接处拿后者产出的**角色名**去索引前者的 `poses` 表：

```python
ff_victim  = _find_char_with_pose(ff_named, _SITTING_POSES)     # 角色名
kf0_victim = _find_char_with_pose(kf0_named, _DOWN_POSES)       # 角色名
... f"FF「{ff_m['poses'][ff_victim]}」→ kf[0]「{kf0_m['poses'][kf0_victim]}」"
#            ^ 类别键映射            ^ 用角色名索引 → KeyError: '杨旭'
```

（本报告初稿把根因写成「两张帧表过滤不同」——**那是错的**：`kf_markers` 就是
`_extract_state_markers` 对 `mid_kfs` 的逐帧投影，两条列表同源，问题只在映射语义。）

**同一根因的第二处入口**（不崩但错）：pre/post 冲突告警把类别键当受害者名打进文案
（实测「+ reclining已「倒地」」，[validation.py:6407](../step01_script_gen/validation.py#L6407) 一带）。

**后果与严重性不匹配**：一个只 append warning 的检查，把整次运行打成 rc=1、无 BLOCK
清单、候选稿全丢。

**已修（2026-09-28，本轮实施）**：两处都改从 `_extract_named_poses` 取角色名与姿态文本；
名册取不到名字时用通用称谓「被打者」+ 类别映射里的**姿态词**（不是类别键）。
**触发条件与告警数量不变**（只改取值与文案）。反例测试
`tests/step01_script_gen/test_kf_temporal_pose_map_identity.py`（4 条，改前全红——
其中一条就是 run 10 的 `KeyError: '杨旭'`）。
**未采纳**「统一异常兜底」作为本条的替代：那是另一项策略，且不得把检查失败当检查通过
（若要加，异常必须降级为显式的 `checker_error` 告警并计入可见面，不能静默放行）。

### N2 ★ 拆分层截断长台词 → 终稿台词门显式失败（1/10 次，rc=1）

run 07 在 576s、`[拆分] 镜头6 → 2 镜` 与一次结构轮之后崩于终稿台词门：

```
diagnosis(step01_plan_infeasible.json): conclusion=dialogue_incomplete, reason=cross_shot_split
  计划原文：…奴家……奴家连他是男是女都没看清……
  终稿旁白：…奴家……奴家连他是男是女都没          ← 切在「都没|看清」之间
```

切点**不是句末边界**（`find_legal_split` 的单一判据只允许句末标点串之后，[plan_feasibility.py:242](../step01_script_gen/plan_feasibility.py#L242)），而尾段「看清……」在终稿里没有可重组的落点 → 门判 `cross_shot_split`。门的行为是对的（fail-closed、不静默落回历史快照），**要治的是拆分器在非法切点落刀**：本批 1/10 次出现。

⚠️ **写入位置尚未确认**（复核意见）：不能因为「接入 `find_legal_split` 单源」这个方向正确，就宣称根因已解决——先要定位那一刀**由哪条路径写入**（候选层同一次也已报过 `not_found`，是同一句的两处症状；拆镜、`short_shot_merge`、`duplicate_shot_merge`、结构轮重写都可能改写 narration），再决定改哪一处。

### N3 ★ KF 结构闸门是绝对判据 → 稿内既有越窗帧会让修复轮永远过不了（1/10 次，但影响机制普适）

```
run02  [REPAIR] KF 结构验收未过 3 处（授权增删 KF 的闸门）：
       ['shot_4: kf2 t_sec=3.5 越出镜长 3', 'shot_5: …', 'shot_11: …']
run02  [REPAIR] 修复未满足接受条件（reason=kf_structure_invalid, resolved=3, …），回退本轮修复
run02  [COMMIT] 提交前修复轮零改善（稿件未变），停止修复
```

逐条核对（`.tmp/agg_run10b.py` 的 C 段自动比对「修复前候选稿」）：**这 3 处越窗帧在修复前就存在**（`preexisting=True`）。机制在代码里：

- [kf_structural_guard.py:70](../step01_script_gen/kf_structural_guard.py#L70) `kf_order_violations(after_shot)` 只校验**修复后**的镜头，是**绝对判据**，不做前后差分；
- 于是**任何**被授权改该镜 `keyframes` 的修复轮都会被判 `kf_structure_invalid` ——哪怕越窗帧与本轮修复无关；
- 本轮→按目标回退（P4 生效）→净改善 0→外层判「零改善」→**停止修复**（run 02 只有 1 个修复轮）。

而越窗帧本身：`kf_time_out_of_shot` 是 `hard` 且 **`repairable=False`**，没有任何轮能修它 → 必进终局阻塞。

**越窗帧从哪来**（生成侧实测，与管线反馈无关——两条会进模型的缺段文案都按 `kf_coverage.analyze` 的段表算中点、夹在镜内，给出 `t=4.5` 的那条 advisory 只进日志、不在 `_REPAIR_PRIORITY_CATEGORIES`）：

```
镜1 dur=4.0  motion_desc「前2秒…；2-4秒…；4秒后…」  kf_t=[1.0, 3.0, 4.5]  ← 4.5 > 4.0
```

模型把**开放尾段「N秒后」当作固定 1 秒**，据此给第 3 帧 `t = N + 0.5`；当 `duration_sec == N` 时必然越窗。B 批 11 份新稿 149 镜里 **22 镜**如此（A 批 10 份 143 镜里 3 镜，且形态不同），占 B 批全部阻塞的可见来源之一（§3.4）。

**已按复核决定实施（2026-09-28）**：`kf_structural_violations` 改**差分**口径——只记「本轮**新引入 / 恶化**」的违例，身份取自违例实质（越窗的 `t` 与镜长、非单调的那对时刻）并**与帧下标无关**，同型按**多重集**抵消（数量变多、`t` 被改大仍算新引入）；**绝对口径不在此放宽**：稿内既有越窗帧照旧由质量门在最终提交处判 blocking（`kf_time_out_of_shot` 等 hard 项）。反例测试见 `tests/step01_script_gen/test_kf_structural_repair.py` 的 5 条差分用例。

### 7.9 审计在新通道上的截断问题（2026-09-28 追加）

20 次批复测的前两次暴露：审计调用 `finish_reason=length`、`content` 为空
（思维链吃光 32000 配额，`reasoning_content` 有内容、正文一个字没吐）→ provider 报
「返回文本为空」→ 审计按 `request_failed`（**不可重试**）处置 → 直接 BLOCK。

**三档 effort 的实测**（冻结稿，每档 1–3 次）：`low` + 上限 64000 → ok（思维链 7.5k）；
`minimal` + 32000 → ok 但思维链 **16.4k**（比 `low` 还长）；`none` + 32000 ×3 → 首答
解析失败 **2/3**，其中一次两次都失败 → `parse_failed`（BLOCK）。
→ 该通道的 effort 档位与思考长度**不成单调**，只有「换一次采样」稳。

**根因**：v6.62.6 契约要求「四个 provider 的截断都经 `truncated_result` 统一落法」，
而 agent_plan 的**空正文分支**漏了这一步——截断被误记成普通失败。**修法**：该分支
空正文 + `finish_reason=length` → `truncated=True`；审计侧把截断并入**既有的**有界重采样
预算（`AUDIT_PARSE_RETRIES`）——同性质（换采样就可能不截断）、不新开一层、传输类仍不重试；
用满仍失败返回状态 `truncated`（fail-closed 不变：提交点只认 `status == "ok"`）。
`AUDIT_MAX_OUTPUT_TOKENS` **维持 32000**：截断那次实测 135s，生产审计超时 180s，
抬上限会把最坏耗时推向超时线（超时属传输类、不可重试）。
