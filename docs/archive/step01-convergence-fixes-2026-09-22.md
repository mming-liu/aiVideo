replacement 契约要求返回**完整**镜头对象（24 字段必填），而授权只覆盖少数路径——
模型把未授权字段措辞写歪一点就判越权、**整条作废**（实测 3/3 被拒、修复轮产出 0；
prompt 已两处要求「逐字照抄原镜」，模型不遵守）。

由**构造保证**，安全性质不弱（差异只在授权路径内，正是原判据本身），原判据保留为纵深防御。

### v6.92（2026-09-22.5）— 切点交给代码

实测把「切在哪」交给模型只会得到三种失败：**不均衡**（子镜仍 11.9s）、**只回一段**
（20.2s 那条直接拒绝拆）、**补字**（原 76 字拼回 120 字）。
关键认识：**「台词逐字连续」是唯一语义约束 → 切在哪是 `(台词文本, 上限)` 的纯函数**。
改为 `_deterministic_narration_cuts()` 按标点边界切 N 段（`N = ⌈需求÷上限⌉`），
模型只撰写视觉字段；采纳时**逐段逐字比对**。

后续自修一处缺陷：只试「均衡」切点会漏掉可行解（可用标点位置不均匀，均衡解恰好让
中间一段 8.7s）→ 改为在标点位置里**穷举**，以「先全部 ≤ 上限、再最小化最长段」为序。

### v6.97（2026-09-22.10）— 「生效单镜上限」收敛为唯一源

v6.93 把项目单镜上限 8s → 15s 时，**3 处写死的 8.0 漏改**，另有多处各算各的。
在 `timecode.py` 落 **`active_shot_cap()`**（`min(视频模型 cap, 项目 MAX_SHOT_DURATION)`）
作为全仓唯一源，8 处全部改为调用它。

**其中 `duration_budget._SHOT_CAP = 8.0` 是实测确认的假 HARD 来源**（确定性实验，用落盘脚本）：

| cap | `duration_budget` HARD 列出的镜头 | 其中**合法**的 |
|---|---|---|
| **8（旧，写死）** | shot11=9.8s、shot13=12.5s、shot15=9.3s、shot17=8.4s | **3 条**（9.8 / 9.3 / 8.4 在 12s 上限下完全合法） |
| **12（现在，生效值）** | shot13=12.5s | 0（这条是真超） |

它 `repaired=False` 且返回 `[]`，所以**不损坏数据**，但会顶高 `_has_hard` 计数、
可能触发无事可修的修复轮，也是早期日志里 `[CONSTRAINT] HARD 未解决 N 处` 偏高的一个来源。
触发条件是正片总时长 > 90s（近期每轮都满足，所以一直在生效）。

**一处记录方式的教训**：`[CONSTRAINT] HARD 未解决` 只打 top-5，而 `duration_budget`
是全局单条违例、排不进前五——**日志里 `grep 不到` 不等于没触发**。这类「有没有生效」
的问题要用**确定性实验**回答（拿落盘脚本直接跑那个约束），不要靠日志推断。

**两处「修法不完全照审核走」的地方（已在审核文档第六节说明理由）**：

1. **不建完整 `ContentManifest`**：需要的是「候选不能提供自己的分母」这条性质，
   用「旧稿导出固定清单」就已具备；原文 span/事件 id 在**合法合并**下粒度会变，
   反而把合并判成退化（正是本次要修的那类「永不收敛」缺口）。致命伤 / 武器归属 /
   事件结果由 P1-2 的身份集合覆盖。
2. **空镜删除暂不改成 report-only**：它是**用户定的产品行为**（F15 合并 + R2b 硬删除），
   所以先登记为**显式受豁免的结构写入者**（`STRUCTURAL_SANCTIONED_WRITERS`）——
   行为零变化，但从「隐式副作用」变成「可审查 + 留 advisory 证据」。
   改成 report-only 只需把它从那个集合里删掉，是注册表级的一行改动（**待你定**）。
3. **语义屏障的红线只划到「结构」，不划到「逐镜文本」**（这条是我在实现中**收窄**的，
   审核原文要求「全部 `_SEMANTIC_SHOT_FIELDS` 变化 → blocking」）：
   `kf_time_window_alignment` 之后还有 **71 个约束**（补景别前缀 / 重建锚点 /
   合规替换 / 冗余清洗…），它们**就是靠写 `prompt`/`ff_desc`/`lf_desc` 工作的**。
   按审核原文实现，每次运行都会必然 BLOCK——那正是本会话反复在修的「自己造
   blocking」。实测两次收窄：先发现「逐镜改写」会全线误报，再发现「hook 的任何
   变化」会误报（`transition_keywords` 会给 hook 追加过渡词），最终红线取
   **镜头数 / 纯重排（`set` 相同而 `order` 不同）/ hook 有无 / 角色 identifier 集合**。
   收窄的依据是**真实链条回归**（16 镜真实 fixture + 全部 71 个审计段约束跑一遍，

### 主线 A：**「prompt 说了、模型不做」→ 改用确定性手段**
